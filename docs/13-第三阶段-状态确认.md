# 13 第三阶段 · 模块四：定期状态确认

> 这是整个系统的时间基准。授权流程能不能启动，全看这里推进到哪个状态。

## 13.1 交付接口

| 接口 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/api/heartbeat/status` | GET | 已登录 | 当前状态，首次访问自动创建配置 |
| `/api/heartbeat/config` | PUT | 已登录 | 修改周期与提醒策略 |
| `/api/heartbeat/confirm` | POST | 已登录 | 完成确认，周期 +1 |
| `/api/heartbeat/records` | GET | 已登录 | 确认历史 |
| `/api/admin/heartbeat/verify-queue` | GET | ADMIN | 待核验队列 |
| `/api/admin/heartbeat/{userId}/verify` | POST | ADMIN | 核验失联成立 |

## 13.2 状态机与"超时不能授权"

```
ACTIVE ──到期──> REMINDING ──提醒耗尽──> VERIFYING ──【人工核验】──> REVIEWING
   ▲                 │                      │                          │
   └─────用户确认─────┴──────────────────────┘                   允许申请授权
```

**最后一跳是人工的。** 代码里没有任何定时任务能写 `REVIEWING` ——
`markReviewing` 只被 `verify()` 调用，而 `verify()` 只挂在管理端接口上。
再长的超时也换不来这一步。这是业务原则第一条"未响应不等于授权"的物理落点。

## 13.3 `cycleNo`：整套幂等体系的核心

用户每确认一次，`cycleNo` 加 1。所有定时任务的更新都带着扫描时读到的 `cycleNo`：

```sql
UPDATE heartbeat_confirm_config
   SET status = 'REMINDING', reminder_count = 1
 WHERE user_id = ? AND status = 'ACTIVE' AND cycle_no = ? AND next_deadline_at <= NOW()
```

**用户在这期间确认了 → 周期号变了 → 这条 UPDATE 影响 0 行 → 旧任务自动失效。**

不需要分布式锁，不需要 `synchronized`，也不需要"任务去检查用户是不是刚确认过"——
条件本身就把这件事表达了。

选 `cycleNo` 而不是 `version` 的理由：这里要防的是"周期已经换了"，
而不是"记录被改过任何字段"。语义更精确，日志也更有信息量
（"跳过 cycleNo=2 的到期记录"比"version 不匹配"清楚得多）。

## 13.4 确认的连锁反应

`POST /api/heartbeat/confirm` 不只是重置计时器：

1. `cycleNo + 1`，截止时间后推
2. 提醒计数清零，状态回到 `ACTIVE`
3. **作废该用户所有未生效的授权案件**（通过 `HeartbeatRecoveryHook`）
4. 写确认流水、写审计

第 3 步在同一事务内 —— 取消失败则整笔确认失败，用户重试即可，
不会出现"人已确认但案件还在跑"的中间态。

**已生效（`AUTHORIZED`）的授权不受影响**，只能由所有者主动撤销（docs/07 Q2）。

### 为什么用 Hook 而不是直接调用授权模块

授权模块**依赖**心跳状态（必须 `REVIEWING` 才能申请），
如果心跳再反向依赖授权，就是循环依赖。

用 `HeartbeatRecoveryHook` 把方向反过来：心跳只声明"我恢复了一个人"，
谁关心谁实现。没有实现时（比如授权模块尚未接入），心跳确认照常完成 ——
这是可选扩展点，不是必需依赖。

## 13.5 定时任务入口

本阶段提供 `scanDue()` 与 `scanRemind()` 两个方法，**尚未挂上调度器**
（第四阶段接入 `@Scheduled` + `job_execution_log`）。方法本身的约束已经就位：

| 约束 | 做法 |
| --- | --- |
| 游标分页 | `user_id > lastId ORDER BY user_id LIMIT 200`，不用 OFFSET |
| 单条失败不中断整批 | 条件更新影响 0 行视为"已失效"，跳过而非抛异常 |
| 可重复执行 | 所有推进都是条件更新，重复执行影响 0 行 |

## 13.6 实测结果

```

```

## 13.7 面试可讲点

1. 为什么用周期号而不是版本号做定时任务的幂等键？
2. "用户超时未确认"和"用户同意交出资产"之间差了几步？为什么这么设计？
3. 用户点确认时，正在进行的授权案件应该怎么处理？已生效的呢？
4. 用接口回调（Hook）而不是直接调用，解决的是什么问题？
5. 定时任务扫描为什么要用游标而不是 OFFSET？
