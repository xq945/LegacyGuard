# 19 关键技术难点复盘

> 按「现象 → 根因 → 解法 → 验证」记录开发过程中真正卡住过的点。
> 其中 4 个是**测试或联调时才发现**的缺陷，靠读代码不会暴露。

---

## 难点 1 · 条件唯一约束：既要唯一，又要能重来

**现象**：同一个所有者与同一联系人，不能有两条有效的关系记录；但撤销之后必须能重新邀请。

**为什么常规做法都不行**：

| 做法 | 问题 |
| --- | --- |
| `UNIQUE(owner_id, contact_user_id)` | 撤销后永远无法再邀请 |
| `UNIQUE(owner_id, contact_user_id, status)` | 两条 `REVOKED` 记录互相冲突 |
| 只在应用层查重 | 并发下两个请求都查到"不存在"，双双插入 |

**解法**：生成列 + NULL 语义。

```sql
active_key VARCHAR(64) GENERATED ALWAYS AS (
    IF(status IN ('PENDING','ACTIVE'), CONCAT(owner_id, ':', contact_user_id), NULL)
) STORED,
UNIQUE KEY uk_active_pair (active_key)
```

依赖 MySQL 的一条行为：**唯一索引允许任意多个 NULL**。
有效关系生成非空值 → 互斥；失效关系生成 NULL → 不参与约束。

同一个技巧还解决了软删除后用户名被永久占用的问题。

**验证**：在真实 MySQL 容器中插入两条 `PENDING` 触发 `ERROR 1062 '1:2'`；
改状态为 `REVOKED` 后可插入多条；再重新邀请成功。

## 难点 2 · 定时任务与用户操作并发：旧任务必须失效

**现象**：心跳到期扫描正准备把用户推进到 `REMINDING`，同一瞬间用户完成了确认，周期已经重置。
如果任务照常推进，刚重置的配置会被错误标记为逾期。

**解法**：用**周期号**做条件更新，而不是版本号。

```sql
UPDATE heartbeat_confirm_config
   SET status = 'REMINDING', reminder_count = 1
 WHERE user_id = ? AND status = 'ACTIVE' AND cycle_no = ? AND next_deadline_at <= NOW()
```

用户确认时 `cycle_no + 1`，任务的 `cycle_no` 条件不成立 → 影响 0 行 → 自动跳过。

**为什么不用 `version`**：这里要防的是"周期换了"，不是"记录被改过任何字段"。
`cycleNo` 语义更精确，日志里也能直接看出"跳过 cycleNo=2 的到期记录"。

不需要分布式锁，也不需要 `synchronized` —— 条件本身就表达了这件事。

## 难点 3 · 审批不等于生效：等待期的全条件复核

**现象**：如果"批准"直接等于"授权"，那么从批准到用户察觉之间没有任何缓冲，
一旦判断有误就无法挽回。

**解法**：拆成两个阶段。

```
REVIEWING ──批准──> WAITING_PERIOD ──到期 + 全条件复核──> AUTHORIZED
```

到期时**重新读库**逐条复核，而不是相信扫描时的快照：

| 复核项 | 不满足时 |
| --- | --- |
| 所有者心跳仍为 `REVIEWING` | → `CANCELLED`（人回来了） |
| 联系人关系仍为 `ACTIVE` | → `CANCELLED` |
| 资产仍属于该所有者且未删除 | → `CANCELLED` |
| 无未处理异议 | → `DISPUTED` |
| 资产未被其他生效案件覆盖 | → `CANCELLED` |

最后用 `WHERE id=? AND status='WAITING_PERIOD' AND version=?` 收尾；
影响 0 行就放弃本次生效，**不重试**。

**验证**：端到端测试中，批准后状态显示 `WAITING_PERIOD` 而非 `AUTHORIZED`；
等待期内访问资产返回 403；把等待期改到过去后触发扫描才变为 `AUTHORIZED`。

## 难点 4 · 事务发件箱：怎么发消息才不丢不重

**两难**：

```
事务内发 MQ   → 事务回滚了，消息已发出（消费者收到指向不存在数据的通知）
先提交再发 MQ → 提交成功、进程崩溃，消息永久丢失
```

**解法**：把"要发消息"变成一条数据，与业务同事务落库。

**关键设计：租约而不是三态机。**

`NEW → PUBLISHING → PUBLISHED` 需要"僵死回收"：实例发到一半崩溃，记录卡在 PUBLISHING 永远发不出去。

改为抢占时把 `next_retry_at` 推到未来 60 秒：

```sql
UPDATE outbox_event SET next_retry_at = NOW() + 60s
 WHERE id = ? AND status = 'NEW' AND (next_retry_at IS NULL OR next_retry_at <= NOW())
```

影响 1 行才算抢到。实例崩溃后 60 秒记录自动重新可领，天然自愈。
代价是极端情况下可能重复发布一次 —— 由消费者幂等吸收。

**另一个必须做的动作**：发送后同步等待 Publisher Confirm。

```java
CorrelationData correlation = new CorrelationData(eventId);
rabbitTemplate.convertAndSend(exchange, routingKey, message, correlation);
Confirm confirm = correlation.getFuture().get(5, SECONDS);
if (!confirm.isAck()) throw ...;   // 才算失败
```

`convertAndSend` 返回不代表 Broker 收到。不等确认就标记 PUBLISHED，
等于把"可能丢消息"伪装成"发送成功"。

## 难点 5 · 消费幂等：唯一索引就是边界

```sql
INSERT IGNORE INTO message_consume_record (message_id, queue_name, status, consumed_at)
VALUES (?, ?, 'SUCCESS', NOW())
```

返回 1 = 首次处理；返回 0 = 已处理过。

**必须和业务处理在同一事务**：处理失败回滚时登记也回滚，下次重投还能正常处理；
若分开提交，就会出现"登记成功但业务没做成，且永远不再重试"。

**验证**：管理端重投同一条事件，通知数与消费记录数都不变。

## 难点 6 · 信封加密：AAD 把密文钉在具体记录上

```
KEK（环境变量） ──包裹──> DEK（每份资产随机 32 字节）──AES-256-GCM──> 明文
```

用 `"asset:" + assetId` 作为 AAD。这样有人把 A 资产的密文行挪到 B 资产的记录上，
解密时 AAD 不匹配会**立刻失败**，而不是悄悄解出别人的内容。

**连带的设计约束**：必须先插入元数据拿到自增 ID，才能加密 —— 因此"插元数据 → 加密 → 插密文"
必须在同一事务里。

**验证**：单元测试断言"换 assetId 解密失败""同一明文两次加密密文不同（IV 随机）"
"篡改密文/标签/包裹密钥均失败"。

## 难点 7 · 登录失败记账与事务的冲突 〔测试中发现〕

**现象**：连续输错 5 次密码，账号却始终不锁定。

**根因**：`login()` 整体包在 `@Transactional` 里。失败路径写登录流水、累加失败计数、写审计，
然后抛出 401 —— **异常让这些写入全部回滚**，失败次数永远涨不上去。

**解法**：`login()` 刻意不加事务，失败路径的写入各自独立提交。

这些记录的是"发生过的事"，不应因为登录本身失败而被抹掉。

## 难点 8 · 拒绝请求返回了 422 而不是 403 〔端到端测试中发现〕

**现象**：陌生人读取他人资产，期望 403，实际返回 422「业务规则不满足」。

**根因**：拒绝路径要写访问流水，但 `access_type` 传了 `null`，而该列是 `NOT NULL`。
插入失败抛 `DataIntegrityViolationException`，被全局异常处理器映射成 422 ——
**覆盖了本该返回的 403**。

**更严重的启示**：留痕这个"辅助动作"失败，居然能改写安全结论。

**解法**：对两条路径区别对待。

| 路径 | 留痕写入失败时 |
| --- | --- |
| **允许**（会返回明文） | 让整个请求失败 —— 没有留痕的敏感数据访问不该放行 |
| **拒绝** | 记 ERROR 日志，返回值仍然是 403/404 |

## 难点 9 · 队列一条消息都收不到，而且不报错 〔链路跑通时才发现〕

**现象**：发件箱状态变成 `PUBLISHED`，消费者却从不触发，没有任何报错。

**根因**：队列绑定的 routing key 写成了 `notify.#`，而事件路由键是 `case.submitted`、
`contact.invited` 这种「领域.动作」格式。`notify.#` 只匹配以 `notify.` 开头的键。

**为什么难发现**：Publisher Confirm 依然返回 ack（Broker 确实收到了），
消息只是没有匹配到任何队列，被静默丢弃。

这正是 docs/05 里强调的：**"Broker 收到了"和"被路由到队列"是两件事**。

**解法**：绑定键改为 `#`；同时用 `publisher-returns` + `mandatory` 让路由失败时打 ERROR 日志。

## 难点 10 · 跨表条件唯一无法用索引表达 〔设计边界，非缺陷〕

**需求**：一个资产同时只能被一个有效案件覆盖。

**为什么做不到声明式约束**：案件的"有效"取决于 `authorization_case.status`，
而资产关联在另一张表 `authorization_asset` —— 跨表的条件唯一在 MySQL 里没有表达方式。

**解法（两层）**：

1. 创建案件的事务内先对资产行 `SELECT ... FOR UPDATE`（**按 ID 排序加锁**避免死锁），
   再查占用情况
2. 生效前的全条件复核会再查一次

**这是必须显式说明的设计边界**。被问"为什么这里没有唯一索引"时，
正确答案是"跨表条件唯一没有声明式表达方式，我们用行锁 + 二次复核替代"，
而不是含糊过去。

## 难点 11 · `X-Forwarded-For` 可以伪造，IP 限流形同虚设

**现象**：端到端测试时用不同伪造 IP 连续试密码，IP 限流一次都没触发。

**根因**：解析客户端 IP 时无条件读取 `X-Forwarded-For`，而这个头由客户端发送、可任意伪造。

**解法**：

1. 默认**不采信**该头（`legacyguard.security.trust-forwarded-headers=false`），
   退化为取 `remoteAddr`
2. 补上**账号维度限流**作为纵深防御 —— 即使换 IP，同一账号的尝试次数也受限
3. 再往下一层是数据库的连续失败锁定，不依赖任何缓存

**验证**：伪造 XFF 的请求，数据库 `login_record.client_ip` 记录的是真实回环地址；
Redis 中 `lg:rate:login:ip:*` 与 `lg:rate:login:user:*` 两个维度的计数 key 都存在。

## 难点 12 · 前后端接口契约缺字段 〔写前端时才发现〕

**现象**：管理端"失联核验"页拿到队列，却无法发起核验。

**根因**：`GET /api/admin/heartbeat/verify-queue` 返回的 DTO 里没有 `userId`，
而核验接口是 `POST /admin/heartbeat/{userId}/verify`。

**为什么单元测试没发现**：测试直接构造了 `HeartbeatConfig`，`userId` 在实体里有，
但转成 Response DTO 时没有带上。

**解法**：DTO 补上字段，并同步前端类型定义。

**启示**：单元测试验证的是"逻辑对不对"，**接口契约的完整性要靠前后端真正对接来暴露**。

---

## 小结：哪些问题只有跑起来才会暴露

| 问题 | 发现方式 |
| --- | --- |
| 登录失败计数回滚 | 端到端：连错 5 次不锁定 |
| 拒绝路径返回 422 | 端到端：期望 403 实际 422 |
| MQ 消息静默丢失 | 端到端：发件箱 PUBLISHED 但通知不出现 |
| 核验队列缺 userId | 写前端时对不上接口 |
| XFF 伪造绕过限流 | 端到端：限流一直不触发 |

这五个都不是"代码写得不好"，而是"没有真正把它跑起来"。
单测覆盖的是局部逻辑，端到端覆盖的是**组件之间的契约**，两者不能互相替代。
