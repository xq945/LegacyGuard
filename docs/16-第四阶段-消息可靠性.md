# 16 第四阶段：中间件与消息可靠性

> 第三阶段的系统在单线程下是对的。这一阶段回答的问题是：
> **当消息会丢、会重、会迟到，当任务会并发、会重跑、会崩溃时，它还对吗？**

## 16.1 完整链路

```
业务事务                                     异步
┌──────────────────────────┐
│ UPDATE authorization_case│
│ INSERT audit_log         │
│ INSERT outbox_event   ───┼──> OutboxPublisher（每 2 秒）
└──────────────────────────┘         │ 抢占（租约 60s）
     要么全部提交，                  │ 发送 + 等待 Publisher Confirm
     要么全部回滚                    ↓
                                  RabbitMQ  lg.event
                                       │ routing key = 事件类型
                                       ↓
                                  lg.notify.queue（持久化）
                                       │ 手动 ack
                                       ↓
                              NotificationConsumer
                                       │ INSERT IGNORE message_consume_record
                                       │ INSERT notification
                                       └─ 失败 → basicNack(requeue=false) → lg.dlx → lg.notify.dlq
```

## 16.2 事务发件箱：解决"两难"

| 做法 | 问题 |
| --- | --- |
| 事务内直接发 MQ | 事务回滚了，消息已经发出去 |
| 先提交再发 MQ | 提交成功、进程崩溃，消息永久丢失 |

发件箱把"要发消息"变成一条**数据**，与业务数据同一事务落库：

```java
@Transactional
void submitCase(...) {
    caseMapper.submit(...);          // 业务数据
    outboxService.append("case.submitted", ...);   // 事件也是数据
}   // 一起提交，或一起回滚
```

## 16.3 租约而不是 PUBLISHING 状态

发布器抢占一条事件的方式是**把 `next_retry_at` 推到未来 60 秒**：

```sql
UPDATE outbox_event SET next_retry_at = NOW() + 60s
 WHERE id = ? AND status = 'NEW' AND (next_retry_at IS NULL OR next_retry_at <= NOW())
```

影响 1 行才算抢到。

**为什么不用 `NEW → PUBLISHING → PUBLISHED` 三态**：三态机需要一个"僵死回收"机制 ——
实例发到一半崩溃，记录就卡在 PUBLISHING 永远发不出去。

租约到期后自动重新可领，天然自愈。代价是极端情况下可能重复发布一次 ——
而重复由消费者幂等吸收。这是"多一层冗余设计换一处简化"的取舍。

## 16.4 必须等 Publisher Confirm

```java
CorrelationData correlation = new CorrelationData(event.getEventId());
rabbitTemplate.convertAndSend(exchange, routingKey, message, correlation);
Confirm confirm = correlation.getFuture().get(5, SECONDS);
if (!confirm.isAck()) throw ...;      // 才算失败，走退避重试
```

`convertAndSend` 返回不代表 Broker 收到。不等确认就把状态改成 PUBLISHED，
等于把"可能丢消息"伪装成"发送成功"。

**退避**：30s → 2min → 10min → 1h，5 次仍失败转 `FAILED`，进入管理端人工处理列表。

## 16.5 消费幂等：唯一索引即边界

```sql
INSERT IGNORE INTO message_consume_record (message_id, queue_name, status, consumed_at)
VALUES (?, ?, 'SUCCESS', NOW())
```

返回 1 = 首次处理；返回 0 = 已处理过，跳过。

**必须和业务处理在同一事务**：处理失败回滚时登记也回滚，下次重投还能正常处理；
若分开提交，就会出现"登记成功但业务没做成，且永远不再重试"。

## 16.6 为什么不 requeue

```java
channel.basicNack(deliveryTag, false, false);   // requeue = false
```

`requeue=true` 会让消息立刻重新入队。如果消费逻辑必然失败（比如载荷格式错误），
就形成死循环，把 CPU 和磁盘日志打满。

有限重试交给发件箱的退避重试；这里只负责"要么处理掉、要么老实承认失败进死信"。

## 16.7 定时任务

| 任务 | 频率 | 幂等依据 | 写执行日志 |
| --- | --- | --- | --- |
| `heartbeatDueScan` | 60s | `cycleNo` | ✅ |
| `heartbeatRemindScan` | 60s | `cycleNo` + 轮次 | ✅ |
| `waitPeriodExpireScan` | 60s | `status` + `version` + 全条件复核 | ✅ |
| `outboxPublishScan` | 2s | 租约 | ❌ 见下 |

**Outbox 扫描不写 `job_execution_log`**：每 2 秒一条，一天四万多条，
很快就会把日志表变成负担，且绝大多数是"扫了个寂寞"。
改为只在确实发布了事件时打应用日志，积压情况通过 `outbox_event` 待发行数观察。

任务本身**无状态**：不判断"当前时间是不是该执行"，而是交给 SQL 的
`WHERE next_deadline_at <= NOW()`。这样系统重启、任务漏跑几轮，
下次扫描会把欠下的一并处理掉，不需要补偿逻辑。

## 16.8 实测结果

### 单元测试

```
总计 94 个用例，0 失败
新增：OutboxPublisherTest 5 / NotificationEventHandlerTest 3 / JobExecutorTest 3
```

### 端到端：完整消息链路

| 步骤 | 结果 |
| --- | --- |
| 发出邀请 | 201 |
| 发件箱新增记录 | +1，状态 `NEW` |
| 发布器投递后 | 状态 `PUBLISHED` |
| 消费者落库 | 通知 +1，消费记录 1 |
| **重投同一事件** | **通知数不变、消费记录不变** —— 幂等生效 |
| 任务执行记录 | 3 条（三个定时任务都在跑） |
| 发件箱概况 | 待发 0，失败 0 |

### 并发测试

| 场景 | 结果 |
| --- | --- |
| **10 个并发建案** | 成功 **1**，其余 409/422，库中只有 1 个案件 |
| **10 个并发批准** | 成功 **1**，其余 409，状态只推进一次 |
| **生效扫描 vs 提异议** | 异议先提交 → 案件停在 `DISPUTED`，扫描影响 0 行 |

最后一项正是"等待期结束与异议提交并发"的场景：谁先提交谁生效，
另一个的条件更新必然影响 0 行 —— 数据库行锁保证了这两条 UPDATE 互斥。

### 修复的一个真实缺陷

第二阶段把队列绑定键写成了 `notify.#`，而事件路由键是 `case.submitted` 这种格式 ——
`notify.#` 只匹配以 `notify.` 开头的键，**一条消息都收不到**，且不会报错。
本阶段改为 `#` 并修正了注释。这类问题只有真正跑通链路才会暴露。
