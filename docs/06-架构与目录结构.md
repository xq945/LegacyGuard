# 06 技术选型、工程结构与加密方案

## 6.1 技术选型与理由

每条都回答三个问题：**为什么用它、备选是什么、代价是什么**。

### 后端

| 技术 | 版本基线 | 为什么 | 备选与取舍 |
| --- | --- | --- | --- |
| Java | 21 (LTS) | 虚拟线程、`record`、`sealed`、模式匹配；LTS 维护期长 | Java 17 也够用，但虚拟线程对 I/O 密集的通知模块有实际收益 |
| Spring Boot | 3.3.x | 生态完整、`jakarta.*` 命名空间、原生支持 GraalVM | 3.x 需注意所有 `javax.*` 依赖都要换 `jakarta.*`，MyBatis-Plus 也必须用 boot3 starter |
| Spring MVC | 随 Boot | 同步阻塞模型对本项目足够，调试和排查链路直观 | WebFlux 收益不明显，反而让事务与调试复杂化 |
| Spring Security | 随 Boot | 认证/授权/方法级注解一体，JWT 集成成熟 | Shiro 更轻但生态弱，安全审计场景下 Spring Security 更"正统" |
| MyBatis-Plus | 3.5.x | CRUD 免手写、条件构造器适合动态查询、分页插件开箱即用 | JPA 的脏检查在大批量任务里不好控；MyBatis 手写 SQL 更透明，复杂查询可控 |
| Jakarta Validation | 随 Boot | 参数校验声明式，统一异常可捕获 | — |
| Springdoc OpenAPI | 2.x | 自动生成接口文档，前后端联调必需 | Swagger 2 已停止维护 |
| SLF4J + Logback | 随 Boot | MDC 支持 `requestId` 串联 | — |

> **Spring Boot 3 的一个坑**：MyBatis-Plus 必须引入 `mybatis-plus-spring-boot3-starter`，用老的 `mybatis-plus-boot-starter` 会因 `javax.*` 找不到类而启动失败。

### 中间件

| 技术 | 版本基线 | 为什么 | 替代方案为何不选 |
| --- | --- | --- | --- |
| MySQL | 8.0 | 事务 + 行锁 + 生成列 + `SKIP LOCKED`，本项目并发控制完全依赖这些 | PostgreSQL 更强，但需求已指定 MySQL；8.0.16 以下没有 CHECK 约束 |
| Redis | 7 | 计数、限流、短期状态，成本低 | v1 不需要它的持久化能力，只当高速 KV 用 |
| RabbitMQ | 3.12 | 需求指定；Publisher Confirm、DLX 机制完整，运维成熟 | Kafka 更适合日志/大数据流，对"任务通知"来说过重 |
| Spring Scheduler | 随 Boot | 单实例定时任务足够，无额外运维成本 | XXL-Job / Quartz 集群模式在 v1 属于过度设计 |

### 前端

| 技术 | 为什么 |
| --- | --- |
| Vue 3 + TS | 组合式 API 适合表单密集的管理后台；TS 让接口 DTO 有类型约束 |
| Vite | 启动快，配置少 |
| Element Plus | 表格、表单、状态标签、分页组件齐全，管理端页面开发量最小 |
| Pinia | 状态管理，存登录态与用户信息 |
| Axios | 拦截器统一注入 token、统一处理 401 跳转 |

### 测试

| 技术 | 用途 | 说明 |
| --- | --- | --- |
| JUnit 5 + Mockito | 单元测试 | 覆盖状态机、Guard 逻辑 |
| Spring Boot Test | 集成测试 | `@SpringBootTest` + Testcontainers |
| Testcontainers | 真实 MySQL/Redis/RabbitMQ | **不 mock 中间件** —— 本项目的正确性恰恰依赖它们的真实行为 |
| Awaitility | 异步断言 | 等待定时任务/消费者完成 |

> **关于 Testcontainers**：需求写的是"在条件允许时"。本机 Docker 已验证可用（MySQL 8.0 / Redis 7 / RabbitMQ 3.12 镜像已存在），因此**默认启用**，不用 H2 替代。用 H2 测 MySQL 特有语法（生成列、`SKIP LOCKED`）会得出错误结论。

### 版本号的处理方式

上表是**基线**。第二阶段会在 `pom.xml` 中实际锁定并用 `mvn dependency:tree` 验证解析结果，把真实版本号回填到 `docs/版本清单.md`。

**不会**在第一阶段就宣称"已验证版本兼容" —— 没有跑过的编译结果不能算数。

### 分层约定（强约束）

| 层 | 允许做 | 禁止做 |
| --- | --- | --- |
| Controller | 参数绑定、`@Valid`、调用 Service、包装响应 | 写业务分支、写 SQL、直接改实体状态 |
| Service | 业务规则、事务、调用多个 Mapper | 返回 Entity 给 Controller（必须转 DTO） |
| Mapper | SQL | 业务判断 |
| DTO | 传输 | 携带 `cipher_text` 以外的敏感字段（也要避免） |

**Entity 不出 Service 层**，这是防止密文/敏感字段意外泄露到响应的最有效手段。

## 6.3 资产加密方案

这是整个项目的安全核心。

### 三层密钥结构

```
KEK (主密钥, 32B)  ── 环境变量注入，永不入库
   │
   ├─ 包裹 ──> DEK (数据密钥, 每份资产一个, 随机生成)
   │              │
   │              └─ AES-256-GCM 加密 ──> 资产明文
   │
   └─ 存库：wrapped_dek, kek_version
```

**为什么不是"主密钥直接加密内容"**：那样主密钥泄露 = 全部资产泄露，且换密钥要重加密所有数据。信封加密让每份资产独立，换 KEK 时只需重新包裹 DEK（数据量小得多）。

### 写入流程

```
1. dek        = SecureRandom(32 bytes)
2. iv         = SecureRandom(12 bytes)          // GCM 推荐 96 bit
3. aad        = "asset:" + assetId              // 附加认证数据
4. (ct, tag)  = AESGCM(dek, iv, plaintext, aad)
5. kekIv      = SecureRandom(12 bytes)
6. wrappedDek = AESGCM(kek, kekIv, dek)  → 存 kekIv 拼在 wrappedDek 前
7. contentHash = SHA-256(plaintext)
8. 存：wrapped_dek, kek_version, cipher_text(ct), iv, auth_tag(tag), content_hash
```

### 读取流程

```
1. 用 kek_version 取对应 KEK
2. dek = AESGCM_decrypt(kek, wrapped_dek)
3. 用 dek + iv + tag + aad 解密 cipher_text     // aad 不匹配则解密直接失败
4. 校验 SHA-256(plaintext) == content_hash
```

**AAD 必须是 `asset:{id}`**：如果有人把 A 资产的密文行直接改到 B 资产记录上，AAD 不匹配会导致解密失败，而不是悄悄解出别人的内容。

### 密钥管理

| 项 | 做法 |
| --- | --- |
| 存放位置 | 环境变量 `LG_KEK_V1=<base64 32字节>`，生产用 Docker secrets |
| 禁止 | 硬编码、放 `application.yml`、提交进 git |
| 启动校验 | `KeyProvider` 在 `@PostConstruct` 校验长度 == 32 字节，否则**启动失败** |
| 轮换 | 支持 `LG_KEK_V2` 并存；新数据用最大版本号；旧数据按 `kek_version` 解密 |
| 丢失后果 | **所有资产永久无法解密**，这是设计如此，需在运维文档中警告 |

### 代码层面的防泄露

- `AssetContentRequest` 重写 `toString()`，不打印 content
- Logback 配置 `ch.qos.logback.classic.filter` 或自定义 `MaskingPatternLayout`，正则过滤疑似长 Base64
- `access_log` 与 `audit_log` 只记 `assetId` 和动作，永不记内容
- 全局异常处理**不把请求体打进错误响应**

## 6.4 Spring Security 配置要点

```
SecurityFilterChain:
  csrf         → disable（无 Cookie 会话，纯 Bearer Token）
  session      → STATELESS
  cors         → 仅放行配置的前端源
  authorizeHttpRequests:
      /api/auth/**          permitAll
      /actuator/health      permitAll
      /api/admin/**         hasRole('ADMIN')
      /api/**               authenticated
  addFilterBefore(JwtAuthFilter, UsernamePasswordAuthenticationFilter)
```

| 要点 | 说明 |
| --- | --- |
| 资源级权限 | `@PreAuthorize` 只做粗粒度；资源归属一律在 Service 里查库判断 |
| 当前用户 | 从 `SecurityContextHolder` 取，**任何接口都不接受前端传入的 userId 作为身份** |
| 禁用/锁定用户 | `JwtAuthFilter` 每次校验后查库确认 `status=0`，即使 token 未过期也拒绝 |
| 密码 | BCrypt，strength 10 |
| 认证失败 | `AuthenticationEntryPoint` 返回 401 + `code=40101`，不默认跳登录页 |

## 6.5 部署拓扑（第六阶段实现，此处先定形）

```yaml
services:
  mysql:        # 8.0, 命名卷持久化
  redis:        # 7
  rabbitmq:     # 3.12-management
  backend:      # 多阶段构建，distroless 或 eclipse-temurin:21-jre
  frontend:     # 多阶段构建，nginx 托管静态文件并反代 /api
```

关键点：

- **KEK 通过 `docker-compose` 的 `secrets` 或 `.env` 注入**，不写进 `Dockerfile`、不打进镜像层
- MySQL 与 RabbitMQ 的持久化卷单独命名，`docker compose down -v` 会连数据一起清空 —— README 里要显著提示
- 后端容器以非 root 用户运行
- 健康检查用 `/actuator/health`，compose 里 `depends_on.condition: service_healthy`
