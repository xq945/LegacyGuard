# 10 第三阶段 · 模块一：用户与权限

> 这是第三阶段的第一个模块，也是其余所有模块的前置依赖 ——
> 没有可信的"当前用户"，后面所有资源归属判断都无从谈起。

## 10.1 交付接口

| 接口 | 方法 | 权限 | 成功码 | 说明 |
| --- | --- | --- | --- | --- |
| `/api/auth/register` | POST | 匿名 | 201 | 注册 |
| `/api/auth/login` | POST | 匿名 | 200 | 登录，返回 JWT |
| `/api/auth/logout` | POST | 已登录 | 200 | 令牌加入黑名单 |
| `/api/users/me` | GET | 已登录 | 200 | 查看自己的资料 |
| `/api/users/me` | PUT | 已登录 | 200 | 修改显示名/邮箱/手机号 |

**注意**：`/api/users/me` 的方法签名里没有 userId 参数。当前用户由
`CurrentUser.id()` 从认证上下文取得。把 URL 或请求体改成别人的 ID 不会产生任何效果。

## 10.2 三层防护的设计

登录保护不是一条规则，而是三道独立的闸门，任何一道被绕过都还有下一道：

| 层 | 机制 | 挡住什么 | 失败时 |
| --- | --- | --- | --- |
| ① IP 维度限流 | Redis 计数 10 次/分钟 | 单机换用户名撞库 | 429 |
| ② 账号维度限流 | Redis 计数 10 次/分钟 | 换 IP 撞同一账号 | 429 |
| ③ 账号锁定 | 数据库 5 次失败锁 15 分钟 | 前两层都被绕过 | 403 |

前两层是限速，第三层是熔断。第三层落在数据库上，不依赖任何缓存，
即使 Redis 挂掉也无法绕过。

## 10.3 五个容易写错的地方

### ① 登录失败不能包在事务里

失败时要写登录流水、累加失败计数、写审计，然后抛出 401。
如果整个方法带 `@Transactional`，抛异常会让这些记录**全部回滚** ——
表现就是"失败次数永远涨不上去"，锁定策略彻底失效。

所以 `login()` 刻意不加事务，这些写入各自独立提交。

### ② 用户不存在时也要跑一次密码哈希

```java
if (user == null) {
    passwordEncoder.matches(request.password(), dummyPasswordHash);  // 消耗等量时间
    ...
}
```

否则"用户不存在"会立刻返回，而"密码错误"要等 BCrypt 算完，
攻击者通过响应时间就能枚举出哪些用户名真实存在。

### ③ 锁定到期判断必须带 `locked_until <= NOW()`

```sql
UPDATE sys_user SET status = 0, locked_until = NULL ...
 WHERE id = ? AND status = 1 AND locked_until IS NOT NULL AND locked_until <= NOW()
```

漏掉时间条件，任何一次登录尝试都能把"还有 10 分钟才解封"的账号提前解锁。

### ④ BCrypt 的 72 字节上限

BCrypt 只处理输入的前 72 个字节，超出部分静默丢弃。25 个中文字符
（75 字节）在字符数上没超限，但字节数已超——两个这样的密码只要前 72 字节
相同就会被判定为同一个。必须显式拒绝，而不是让用户以为设了长密码。

### ⑤ `X-Forwarded-For` 默认不采信

该头由客户端发送，可以任意伪造。无条件信任它意味着攻击者每次换一个值，
IP 限流就完全失效。

本项目的处理：默认关闭（`legacyguard.security.trust-forwarded-headers=false`），
退化为取 `remoteAddr`。只有部署在会覆盖该头的可信代理后面时才开启。

## 10.4 实测结果

### 单元测试

```
AuthServiceTest  13 个用例  （注册 3 / 登录 8 / 登出 2）
JwtProviderTest   9 个用例
合计             22 个，0 失败
```

### 端到端（真实服务 + 真实 MySQL/Redis）

| 验证项 | 期望 | 实际 |
| --- | --- | --- |
| 注册 | 201 | ✅ 201 |
| 重复注册 | 409 | ✅ 409 该用户名已被占用 |
| 纯字母密码 | 400 | ✅ 400 密码必须同时包含字母和数字 |
| 登录 | 200 + token | ✅ |
| 带令牌取资料 | 200 | ✅ |
| 不带令牌取资料 | 401 | ✅ |
| 修改显示名 | 200 | ✅ |
| 非法邮箱 | 400 | ✅ |
| 登出 | 200 | ✅ |
| **登出后原令牌访问** | 401 | ✅ 黑名单即时生效 |
| 连续 5 次错误密码 | 第 6 次锁定 | ✅ 正确密码也返回 403 |
| 伪造 `X-Forwarded-For` | 应被忽略 | ✅ 库中记录的是真实回环地址 |

### Redis 侧确认

```
lg:rate:login:ip:0:0:0:0:0:0:0:1       = 3   (TTL 52s)
lg:rate:login:user:v_1793168889         = 1   (TTL 51s)
lg:jwt:blacklist:0737fdc0-...           (TTL = 令牌剩余有效期)
```

两个限流维度都确实在计数，黑名单 TTL 与令牌寿命一致。

## 10.5 本模块未做的事

- 刷新令牌（刻意不做，用 30 分钟短令牌替代）
- 找回密码 / 邮箱验证（v1 无邮件服务）
- 管理员账号创建接口（由 `sql/demo-data.sql` 初始化）

## 10.6 面试可讲点

1. 为什么登录失败时的记账不能和"抛出 401"处在同一个事务里？
2. 用户不存在时为什么要跑一次假的密码校验？
3. 为什么限流要同时按 IP 和账号两个维度？只做其中一个会被怎么绕过？
4. JWT 无法主动失效，登出是怎么实现的？Redis 挂了会怎样？
5. `X-Forwarded-For` 为什么不能无条件信任？
