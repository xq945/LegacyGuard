# 12 第三阶段 · 模块三：可信联系人

## 12.1 交付接口

| 接口 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/api/contacts/invitations` | POST | 已登录 | 按用户名邀请已注册用户 |
| `/api/contacts/invitations/{id}/accept` | POST | 被邀请人本人 | 接受邀请 |
| `/api/contacts/invitations/{id}/reject` | POST | 被邀请人本人 | 拒绝邀请 |
| `/api/contacts` | GET | 已登录 | 我邀请的人 + 邀请我的人 |
| `/api/contacts/{id}` | DELETE | 仅所有者 | 撤回邀请 / 撤销关系 |

## 12.2 状态机

```
PENDING ──接受──> ACTIVE ──撤销──> REVOKED
   │
   ├──拒绝──> REJECTED
   └──撤回──> REVOKED
```

只有 `ACTIVE` 的联系人才能发起授权申请。

## 12.3 唯一性是怎么保证的

需求：同一对用户之间只能有一条有效关系，但**撤销后必须能重新邀请**。

如果直接把 `(owner_id, contact_user_id)` 做成唯一索引，撤销后就永远邀请不了了。
如果把 `status` 放进唯一索引，两条 `REVOKED` 记录会互相冲突。

采用**生成列 + NULL 语义**：

```sql
active_key VARCHAR(64) GENERATED ALWAYS AS (
    IF(status IN ('PENDING','ACTIVE'), CONCAT(owner_id, ':', contact_user_id), NULL)
) STORED,
UNIQUE KEY uk_active_pair (active_key)
```

MySQL 的唯一索引允许多个 NULL。有效关系有值 → 互斥；失效关系为 NULL → 不参与约束。

## 12.4 两处刻意的"信息不泄露"

| 场景 | 返回 | 理由 |
| --- | --- | --- |
| 不是我的关系，或关系不存在 | 一律 404 | 不让人通过返回码探测别人是否存在某条关系 |
| 无法接受别人的邀请 | 404 而不是 403 | 同上：403 等于承认"这条邀请存在，只是你不能动" |

而**状态冲突**（已处理过的邀请）返回 409 —— 这时关系已经被我看到过了，
冲突信息反而有用。

## 12.5 撤销关系不影响已生效授权

这是 docs/07 Q2 的决策落地：

- 撤销关系 → 只阻止**未来**的授权申请
- 已经 `AUTHORIZED` 的案件不受影响，只能由所有者单独撤销

理由：授权是用户在清醒时通过完整流程做出的独立意愿表达，
不应被"关系变更"这类间接操作静默收回。
