# 15 第三阶段 · 模块七/八：通知中心与安全审计

## 15.1 通知中心

### 接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/notifications` | GET | 我的通知，支持 `unreadOnly` |
| `/api/notifications/unread-count` | GET | 未读数量 |
| `/api/notifications/{id}` | GET | 详情 |
| `/api/notifications/{id}/read` | POST | 标记已读 |
| `/api/notifications/read-all` | POST | 全部已读 |

### 幂等靠数据库，不靠判断

`notification.dedup_key` 上有唯一索引。同一件事（例如"用户 3 第 2 周期第 1 轮提醒"）
无论被触发多少次，库里只会有一条。写入撞到唯一约束时捕获 `DuplicateKeyException` 并静默跳过。

**为什么不先查再插**：并发下两个请求可能都查到"不存在"然后都插入。
唯一索引是唯一可靠的幂等边界。

### 当前接入的通知点

| 触发 | 接收者 | 类型 |
| --- | --- | --- |
| 发出邀请 | 被邀请人 | `CONTACT_INVITED` |
| 接受邀请 | 所有者 | `CONTACT_ACTIVATED` |
| 提交案件 | 所有者 | `CASE_SUBMITTED` |
| 批准进入等待期 | 所有者 | `CASE_WAITING_PERIOD` |
| 驳回 | 申请人 | `CASE_REJECTED` |
| 提出异议 | 另一方 | `CASE_DISPUTED` |
| 授权生效 | 双方各一条 | `CASE_AUTHORIZED` |
| 撤销授权 | 申请人 | `CASE_REVOKED` |

### 通知失败不影响业务

`safeNotify()` 用 try-catch 包住：业务状态已经变更，一条站内信写失败不该让审批回滚。
需求原话是「通知失败不能直接导致业务状态回滚」。

### 第三阶段 vs 第四阶段

**当前是同步写库**：业务事务内直接插入 `notification`。
**第四阶段改为事务发件箱 + RabbitMQ**：业务事务只写 `outbox_event`，
独立发布器投递，消费者落库。届时 `NotificationService.send` 的语义不变，调用方不用改。

之所以现在就能这么设计：`dedup_key` 唯一索引让同步和异步、投递一次和重投多次的结果完全一致。

## 15.2 安全审计

### 接口

`GET /api/audit/logs` —— 支持按动作、对象类型、对象 ID、时间范围筛选。

### 最关键的一行

```java
Long actorScope = CurrentUser.isAdmin() ? null : CurrentUser.id();
```

**身份范围由服务端决定，不接受客户端传 `actorId`。**
如果允许传，任何人都能翻别人的操作历史 —— 这恰恰是审计系统最不该出现的问题。

管理员传 `null` 表示"不限操作人"，可以查全部。

### 写入时的三条铁律

1. **与业务同事务**：业务成功而审计失败，等于做了一次没有痕迹的操作
2. **只增不改**：Mapper 接口里根本没有 update/delete 方法
3. **不含敏感内容**：`detail` 里禁止出现密码、令牌、资产明文、加密密钥

### 审计 vs 登录流水 vs 访问流水

| 表 | 记什么 | 为什么要分开 |
| --- | --- | --- |
| `audit_log` | 业务决策（谁批准了什么） | 量中等、需长期保留 |
| `login_record` | 每一次认证尝试（含失败） | 量大、结构规整、用于风控分析 |
| `asset_access_log` | 每一次读取敏感内容的尝试（含被拒） | 越权分析的关键证据 |

## 15.3 实测结果

| 验证项 | 期望 | 实际 |
| --- | --- | --- |
| 被邀请人未读数 | 1 | ✅ `CONTACT_INVITED` |
| 邀请人接受后未读数 | 1 | ✅ `CONTACT_ACTIVATED` |
| 案件提交后通知 | `CASE_SUBMITTED` | ✅ |
| 标记单条已读 | 200，未读减少 | ✅ 剩余未读 1 |
| **普通用户查审计** | 只有自己的记录 | ✅ 总数 4，非本人记录 0 |
| 查看他人通知 | 404 | ✅ |

普通用户查到的动作类型：`ASSET_CREATE`、`CONTACT_INVITE`、`LOGIN_SUCCESS`、`REGISTER` —— 都是自己的操作。

## 15.4 面试可讲点

1. 通知的幂等为什么用数据库唯一索引而不是"先查再插"？
2. 通知发送失败为什么不能回滚业务？如果反过来会怎样？
3. 审计表为什么不允许 update/delete？接口设计层面怎么保证？
4. 为什么审计查询的操作人范围必须由服务端决定？
5. 审计日志、登录流水、访问流水为什么要分三张表？
